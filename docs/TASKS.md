## 1. 项目简介

用户用 iPhone 13 Pro 拍一张照片，照片里是一块贴有 4 个 ArUco 码的 A4 底板，底板上放着若干电子零件。网页依次完成以下工作：

1. 读取照片和 EXIF，得到相机内参
2. 识别 ArUco 码，求出"底板毫米坐标 → 图像像素"的单应性矩阵 H，并生成底板正射图
3. 由 H 和内参反推拍照时手机的位置和朝向
4. 用 YOLO26n（ONNX）检测零件，把检测框映射到底板毫米坐标（支持视差修正）
5. 在 Three.js 里按真实尺寸重建桌面、底板、零件和拍照的手机，并播放"照片 → 3D"转场动画
6. 虚拟机械臂用逆运动学依次抓取零件，放进对应类别的料盒

整个系统是纯前端静态网页，不需要后端。

## 4. 坐标系约定（所有模块必须统一）

| 坐标系 | 原点 | 轴向 | 单位 |
| --- | --- | --- | --- |
| 图像 | 照片左上角（已按 EXIF 方向转正） | u 向右，v 向下 | 像素 |
| 底板（世界） | 底板靠近操作者的左下角 | X 向右，Y 远离操作者，Z 垂直板面向上（右手系） | mm |
| OpenCV 相机 | 镜头光心 | x 右，y 下，z 沿拍摄方向 | mm |
| Three.js | 与底板原点相同 | x = X，y = Z，z = −Y | 1 单位 = 1 mm |

- 底板坐标 ↔ Three.js 坐标的转换只写在 `src/math/coords.js` 里（`toThree(X, Y, Z)`、`fromThree(v)`），其他地方一律使用底板坐标。
- 位姿约定：底板点 Pw 变换到相机坐标为 Pc = R·Pw + t，手机光心在底板坐标系里的位置为 C = −Rᵀt。
- H 的方向：底板 (X, Y, 1) → 像素 (u, v, 1)。Hinv 方向相反。

## 5. 数据接口

在 `src/state.js` 里用 JSDoc 定义以下类型，各模块函数的输入输出都使用这些类型：

```js
/** 照片 */
ImageInput = { bitmap, width, height, fileName,
               exif: { focal35, focalMm, lensModel, make, model } }

/** 模块 1：内参（对应当前照片的实际分辨率和方向） */
Intrinsics = { fx, fy, cx, cy, width, height, source: 'exif' | 'calib' | 'truth' }

/** 模块 2 */
Marker     = { id, corners: [[u,v],[u,v],[u,v],[u,v]] }  // 顺序：码自身的左上、右上、右下、左下
BoardCalib = { markers: Marker[], H, Hinv, reprojErrPx, rectified /* canvas */ }

/** 模块 3 */
CameraPose = { R /* 3×3 */, t /* [3] */, position /* C: [X,Y,Z] */,
               heightMm, pitchDeg, reprojErrPx }

/** 模块 4 */
Detection = { cls, name, score, box: [x1, y1, x2, y2] }  // 原图像素
Part      = { id, cls, name, score, x, y, heightMm,
              xPlane, yPlane,      // 方法 1（不修正）的结果
              reachable }           // x, y 为当前选用方法的结果

/** 模块 6 */
PickTask  = { partId, binId, from: [x, y, z], to: [x, y, z] }

/** 合成图真值（步骤 3 生成） */
GroundTruth = { intrinsics, R, t, position, pitchDeg,
                markers: Marker[],
                parts: [{ cls, x, y, heightMm, box }] }
```

流程状态机：`idle → imageLoaded → calibrated → posed → detected → sceneBuilt → sorting → done`。每一步写入 state 后发出事件；某一步失败时停在当前状态，信息面板显示原因，并允许单独重跑这一步。

#### 步骤 3：合成测试图生成器

**目标：** 在还没有真实照片的情况下，生成带精确真值的"假照片"，用来自动检验后面每个模块算得对不对。

**实现要点：**
- `synth.html`：用 Three.js 离屏渲染一张 4032 × 3024 的图片。内容包括：

  - `GroundTruth` JSON：内参、R、t、手机位置、俯角、每个码 4 个角点的像素坐标、每个零件的 (x, y)，以及零件 3D 包围盒投影到图像上得到的 box

### 阶段二：视觉几何

#### 步骤 4：读取照片与相机内参（模块 1）

**目标：** 正确读入照片（方向、尺寸、EXIF），算出内参。

**实现要点：**
- `image.js`：用 `createImageBitmap(file, { imageOrientation: 'from-image' })` 按 EXIF 方向转正；用 exifr 读 `FocalLengthIn35mmFormat`、`FocalLength`、`LensModel`、`Make`、`Model`。HEIC/HEIF 文件直接提示"请在 iPhone 设置 → 相机 → 格式中选择'兼容性最佳'"。
- `intrinsics.js` 导出纯函数：
  - `fromExif(focal35, width, height)`：f = focal35 × √(W² + H²) ÷ 43.27，fx = fy = f，cx = W/2，cy = H/2
  - `fromCalib(calib, width, height)`：读 `intrinsics.json`（参考分辨率 4032 × 3024，横向）
    - 分辨率不同时，fx、fy、cx、cy 都乘以 s = 实际宽 ÷ 参考宽
    - 竖拍（顺时针转 90°）时，fx' = fy，fy' = fx，cx' = 参考高 − cy，cy' = cx
- 镜头检查：`focal35 ≠ 26` 时，信息面板显示黄色警告"可能切换了镜头（当前等效焦距 xx mm）"。
- （实现补充）`fromCalib` 增加可选第 4 个参数 rotation（照片相对传感器顺时针旋转的角度，由 EXIF Orientation 得到：6 → 90°、3 → 180°、8 → 270°），省略时按宽高判断，竖图视为顺时针 90°；`ImageInput.exif` 增加 `orientation`。标定文件格式：`{ fx, fy, cx, cy, width, height, dist, rms }`，未标定时 `public/intrinsics.json` 为只含说明的占位文件。
- （实现补充）照片没有 EXIF（例如微信转发未选"原图"）时按默认 26 mm 估算并提示。默认来源：合成图用真值；有标定文件且是主摄、宽高比一致时用标定文件；否则用 EXIF。
- 信息面板显示：文件名、分辨率、等效焦距、镜头型号、fx、内参来源。界面上可以切换 EXIF / 标定文件（没有 `intrinsics.json` 时禁用该选项）。

**单元测试：** (26 mm, 4032 × 3024) → fx 在 3028 ± 1；竖拍换算；分辨率缩放。

**验收标准：**
- [ ] 【需要用户】上传一张 iPhone 横拍 JPEG 和一张竖拍 JPEG，调试视图里方向都正确
- [ ] 横拍照片面板显示 4032 × 3024、26 mm、fx ≈ 3028
- [ ] 上传 HEIC 文件时出现格式提示
- [ ] `npm test` 通过

#### 步骤 6：单应性与正射图（模块 2 下半部分）

**目标：** 求出 H，生成"从正上方看"的底板图。

**实现要点：**
- `homography.js` 纯函数：
  - `solveHomography(worldPts, imagePts)`：归一化 DLT。两组点各自平移到质心、缩放到平均距离 √2，构造 2N × 9 矩阵，用 ml-matrix 做 SVD 取最小奇异值对应的向量，最后反归一化。
  - `applyH(H, p)`、`invert3(H)`、`reprojError(H, worldPts, imagePts)`
- 角点的底板坐标：码中心 (cx, cy)、边长 s 时，左上 (cx − s/2, cy + s/2)，右上 (cx + s/2, cy + s/2)，右下 (cx + s/2, cy − s/2)，左下 (cx − s/2, cy − s/2)。
- 至少 1 个码就计算；少于 4 个码时给出精度警告。重投影误差 > 3 像素时提示重拍。
- `rectify(bitmap, H, pxPerMm = 2)`：输出 594 × 420 的 canvas。画布第 i 行第 j 列对应底板坐标 X = j / 2，Y = 210 − i / 2（画布顶部是底板远端），用 H 找到原图像素并取色（双线性插值）。
- 调试视图增加一个"正射图"小窗。
- （补充，2026-10-12）打印机会把内容整体印偏 1–2 mm，纸张的实际位置与设计位置不完全一致。标定时同时测量纸边（`boardCheck.js` 的 `measurePaper`：沿每条纸边采样，亚采样插值，稳健拟合直线，四线求交得到纸张四角），结果存入 `BoardCalib.paper`（四角底板坐标、纸张尺寸、打印比例）。底板坐标仍以码为准；位姿叠加和后续 3D 底板的外框用实测纸张轮廓，测不出时用设计尺寸。打印比例偏差 > 2% 时提示重新打印。
- （实现补充）按项目的像素约定取像素中心：第 i 行第 j 列对应 X = (j + 0.5) / 2，Y = 210 − (i + 0.5) / 2（与上面的公式差半个像素，即 0.25 mm）；超出原图的区域透明。采样部分是纯函数 `rectifyPixels`，`rectify` 只负责 canvas。由码求 H 的流程为 `boardHomography`（含少于 4 个码、重投影误差 > 3 像素的提示）。正射图小窗上用虚线画出设计的码位置，便于检查。合成图另外显示"单应性 vs 真值"：底板上每 10 mm 一个点，比较 H 与真值位姿的投影。

**单元测试：** 用已知 H 生成点对，能恢复出 H；加 0.5 像素噪声后重投影误差 < 1 像素。

**验收标准：**
- [ ] 合成图的重投影误差 < 1.5 像素；真实照片 < 3 像素
- [ ] 正射图方正不变形：ID3 在左上、ID2 在右上、ID0 在左下、ID1 在右下，码都是正方形
- [ ] `npm test` 通过

#### 步骤 7：手机位姿反推（模块 3）

**目标：** 由 H 和 K 求出拍照时手机的 R、t 和位置。

**实现要点：**
- `pose.js` 纯函数 `poseFromHomography(K, H, worldPts, imagePts)`：
  1. B = K⁻¹H，三列记为 b₁、b₂、b₃
  2. λ = 2 ÷ (‖b₁‖ + ‖b₂‖)；r₁ = λb₁，r₂ = λb₂，t = λb₃
  3. 若 t 的 z 分量 < 0，r₁、r₂、t 全部取反
  4. r₃ = r₁ × r₂，R = [r₁ r₂ r₃]；用 SVD 正交化：R = U·Vᵀ
  5. C = −Rᵀt；heightMm = C 的 Z 分量
  6. 光轴方向 d = Rᵀ·(0, 0, 1)，pitchDeg = asin(−d_z)（90° 表示垂直向下拍）
  7. 用 K[R | t] 重投影全部角点，求平均误差 reprojErrPx
- 调试视图增加"位姿叠加"开关：用 K[R | t] 把底板外框、4 个码的方框和底板坐标轴（X 红、Y 绿、Z 蓝，长 100 mm）投影画在原图上。
- 信息面板显示："手机离桌面 xx.x cm，俯角 xx.x°，重投影误差 x.xx 像素"。
- （实现补充）上述 7 步得到解析解后，增加第 8 步：以解析解为初值，用 Levenberg–Marquardt 优化 6 个位姿参数，最小化全部角点的重投影误差（`refinePose`）。单元测试中 0.5 像素噪声下平均位置误差 0.53 → 0.28 mm，最大位置误差 1.39 → 0.98 mm；真实照片的位姿重投影误差约降低 1/3（剩余部分来自纸面不平、镜头畸变等，单应性多 2 个自由度能吸收）。注意：接近正上方拍摄时焦距误差几乎不影响重投影误差，但按比例影响高度，高度精度取决于内参标定。
- （补充）由照片估计焦距（`estimateFocal`）：把焦距 f（fx = fy，主点取图像中心）作为第 7 个参数一起做 LM，并用舒尔补求 f 的不确定度。斜拍（约 45°–75°）时透视明显，f 能准确估计（单元测试中 0.5 像素噪声下误差 < 1%）；接近正上方时 f 与高度可互换，不确定度趋于无穷，判为不可用。相对不确定度 < 1% 时，内参来源多一个"照片估计"（`Intrinsics.source = 'self'`），与当前内参差异显著时位姿卡片提示并提供"改用估计的焦距"按钮。位姿重投影误差明显大于单应性重投影误差时提示"内参可能不准"。求出的高度 ≤ 0 时视为失败。合成图显示位置 / 俯角 / 姿态相对真值的误差（`evaluate.js` 的 `poseTruthError`）。

**单元测试（纯数学，不经过 Three.js）：** 随机生成 20 组位姿（高度 250–500 mm，俯角 40°–90°），用针孔模型投影角点：无噪声时位置误差 < 0.1 mm；加 0.5 像素噪声时位置误差 < 5 mm，角度误差 < 0.5°。

**验收标准：**
- [ ] 3 张合成图：位置误差 < 5 mm，俯角误差 < 0.5°（面板显示与真值对比）
- [ ] 真实照片打开位姿叠加，底板外框和码方框贴合照片里的实物
- [ ] 【需要用户】拍照时用卷尺量镜头离桌面的高度，与系统给出的高度相差 < 5%
- [ ] `npm test` 通过

#### 步骤 9：虚拟手机与"照片 → 3D"转场

**目标：** 在 3D 场景里显示拍照的手机，并实现转场动画。

**实现要点：**
- `phone.js`：
  - 手机模型：71.5 × 146.7 × 7.65 mm 圆角盒，镜头（小圆柱）位于光心 C；机身按照片方向摆放（竖拍时长边沿图像纵向）。
  - 视锥：从 C 到照片四角在底板平面上的落点各画一条线（落点 = Hinv 作用在照片四角上）。某个角的射线打不到底板平面时，只画 600 mm 长。
  - 底板上画出照片视野范围的四边形轮廓。
- 虚拟相机设成手机位姿：
  - 位置 = toThree(C)
  - 朝向：相机三个轴在底板坐标系里 = Rᵀ·diag(1, −1, −1) 的三列，各自用 toThree 转换后，用 `Matrix4.makeBasis` 生成姿态
  - 纵向 fov = 2·atan(H ÷ 2fy)，换算成度；aspect = W ÷ H
- `transition.js`（总时长约 4 秒，可重播）：
  1. 3D 画布容器改成照片的宽高比，原照片用 `<img>` 盖在画布上
  2. 虚拟相机放在手机位姿上
  3. 1 秒内照片透明度 1 → 0，同时零件模型从板面"长出来"（这一步暂时没有零件，先留接口）
  4. 2 秒内相机从手机位姿飞到默认全景视角（位置线性插值 + 四元数 slerp，缓动 easeInOutCubic），手机模型和视锥逐渐显示
  5. 画布恢复全屏，启用 OrbitControls
- 提供"对比"按钮：相机停在手机位姿，照片以 50% 透明度叠加，用来检查是否重合。
- （实现补充）
  - 视锥落点用视线与 Z = 0 平面求交（`pinhole.js` 的 `photoFootprint`），与 Hinv 作用在四角上等价，但能直接判断视线是否朝下、打不到时按 600 mm 截断。
  - 手机机身按 EXIF 方向摆放（`phone.js` 的 `phoneLayout`；没有方向时按照片宽高判断），镜头在光心 C、位于机身背面距两边各约 14 mm 处。
  - 主点不在图像中心时（例如标定内参），虚拟相机用 `setViewOffset` 平移画面。
  - 盖在画布上的照片用 canvas 绘制（ImageBitmap 不能直接作为 `<img>` 的源）。
  - 转场各段：停 0.3 s → 照片淡出 1 s → 飞行 2 s（画面区域同时从照片比例恢复全尺寸）→ 停 0.3 s，共约 3.6 s。
  - "照片比例的画布"用渲染视口 + 裁剪区域实现（`world.setFrame`），画布本身尺寸不变，区域外填视图底色；每帧改画布尺寸会清空绘图缓冲，造成闪烁。转场每帧更新后立即渲染；开始时先让手机、零件全部可见完整渲染一帧（照片随即盖上，看不到），避免它们第一次出现时编译着色器、生成阴影而卡顿。
  - 手机模型不投影（悬空机身在桌面上的大块阴影干扰观察）。
  - 全景视角要把手机也装进画面：手机明显偏到底板一侧时从垂直于偏移的方向侧看（手机不挡底板、高度看得清），手机大致在底板正上方时从右前方 40° 看；距离按所有点的投影计算。没有手机时仍是步骤 8 的默认视角。
  - 新照片读入后手机与转场清空；有新位姿时，切到 3D 视图自动播放一次转场。

### 阶段五：机械臂与分拣

#### 步骤 11：机械臂模型与逆运动学

**目标：** 机械臂能把指尖准确送到底板上任意一点。

**实现要点：**
- `ik.js` 纯函数（坐标都相对底座）：
  - `ik(target, ARM)`：
    - θ₀ = atan2(y, x)，r = √(x² + y²)，z' = z + L3 − L0
    - D = (r² + z'² − L1² − L2²) ÷ (2·L1·L2)；|D| > 1 时返回 `reachable: false`
    - θ₂ = −arccos(D)（肘部朝上）
    - θ₁ = atan2(z', r) − atan2(L2·sin θ₂, L1 + L2·cos θ₂)（从水平面量起）
    - θ₃ = −π/2 − θ₁ − θ₂（保证夹爪竖直向下）
  - `fk(angles, ARM)`：返回指尖位置，用于测试和显示
- `arm.js`：用 Three.js 基础几何体搭出层级结构：底座（绕 Z 旋转）→ 肩关节 → 大臂 → 肘关节 → 小臂 → 腕关节 → 夹爪（两根手指，可开合）。外观干净、工业风。
- `bins.js`：按 `BINS` 摆放开口料盒，盒子侧面写类别名。
- 调试模式：在 3D 视图里点击底板任意位置，机械臂运动到该点正上方 `approach` 高度处，信息面板显示 fk 计算的指尖位置与目标的误差；够不到的点显示红色提示。

- （实现补充）
  - `ik.js` 另外导出 `fkChain`（各关节位置）、`ikWorld / fkWorld`（底板坐标版本）、`lerpAngles`（关节空间插值：θ₀ 走最短方向，θ₃ 由 θ₁、θ₂ 推出，途中夹爪始终竖直向下）。
  - 腕部转动关节 θ₄：`ik(target, ARM, { gripYaw })` 让两指连线在水平面内的方向 = gripYaw（θ₀ + 90° + θ₄ = gripYaw，θ₄ 取 ±90° 以内）；不给 gripYaw 时 θ₄ = 0。关节角数组变为 5 个。
  - 限位与碰撞（`checkPose`）：每段连杆近似为胶囊体（`ARM_SHAPE`），检查夹爪与底座 / 立柱 / 大臂、小臂与底座 / 立柱 / 肩关节的距离，肘关节折叠 ≤ 165°，各关节不低于桌面。`ik` 默认做这些检查，不通过时返回 `reachable: false` 和原因（例如"太靠近底座，夹爪会碰到底座"）。`pathClear` 检查关节空间插值途中是否碰撞，碰撞时先回初始姿态再过去。
  - 大臂做成两片侧板的叉形结构，小臂折进两片侧板之间，所以够到离底座最近的远边时不会互相穿插。
  - `arm.js` 的层级与 ik.js 的关节一一对应（转台绕 y、三个俯仰关节绕局部 z、腕部转动绕夹爪轴），有单元测试核对模型层级算出的指尖与 fk 一致、两指连线方向与 ik 约定一致。
  - 初始姿态收拢竖起，指尖在底板远边外侧上方 (148.5, 220, 200)，不伸到底板上方。
  - 默认视角同时装进料盒和机械臂（机械臂在底板远端，不挡视线）。
  - 调试模式：3D 视图"机械臂调试"按钮打开后，点击（拖动不算）底板或桌面，机械臂移到该点正上方 approach 高度；目标处显示圆环和竖线，够不到时变红并在面板说明原因。

**单元测试：** 在可达范围内随机取 200 个点，`fk(ik(p))` 与 p 的误差 < 0.01 mm；明显超出范围的点返回不可达。

**验收标准：**
- [ ] 点击底板四个角附近和中心，指尖都准确到达（面板误差 < 0.1 mm）
- [ ] 动作中各段连杆不脱节，夹爪始终竖直向下
- [ ] 料盒都在可达范围内
- [ ] `npm test` 通过

#### 步骤 12：分拣规划与抓取动画

**目标：** 机械臂自动把全部零件分拣进对应料盒。

**实现要点：**
- `planner.js` 纯函数 `plan(parts, BINS, ARM) → { tasks: PickTask[], skipped: Part[] }`：先排除不可达零件，然后用贪心最近邻排序（从当前夹爪位置出发，每次选最近的零件）。

  1. 移到零件正上方 `approach` 高度
  2. 下降到零件半高处
  3. 夹爪闭合，用 Three.js 的 `attach` 把零件挂到夹爪节点下
  4. 抬起到 `approach` 高度
  5. 移到对应料盒正上方

- 界面：任务列表（执行中的一项高亮、完成的打勾）、开始 / 暂停 / 重置按钮、速度滑块（0.5×–3×）。不可达零件标红，并列在"已跳过"里。
- 重置后，零件回到原位，机械臂回到初始姿态。

- （实现补充）
  - `plan(parts, BINS, ARM, { start })`：指尖下到离板面 0.5 mm 处夹取（指尖垫片高 10 mm，正好包住躺平零件的中部；文档原写"零件半高处"，按用户要求改低）；长条零件（电阻、螺丝、LED）夹爪两指连线垂直于长轴（用步骤 10 估计的朝向），LED 夹在灯体中部（沿长轴离中心 9.25 mm），电容夹爪不转。抓取点、上方悬停点、料盒放置点、盒口上方悬停点都要通过逆运动学和碰撞检查，否则零件进"已跳过"并写明原因。贪心最近邻的起点是机械臂初始姿态的指尖，每放完一个从料盒上方继续选。

  - 料盒内摆放（后改为落下散开，见变更记录）：长条零件搬运途中转动夹爪，放下时沿料盒长边（Y）摆放，每层左右 2 个（x = ±10 mm）；圆形零件每层 2 × 2 个（±12、±14 mm，电容删除后暂时用不到）；放满一层叠到上一层（层高 = 该类零件高度）。零件随夹爪转过的角度 Δ = (θ₀ + θ₄)放 − (θ₀ + θ₄)取，放置点按 Δ 迭代求出，使零件中心正好落在盒内位置上（有单元测试）。
  - 动作序列（`robot/sequence.js`，纯函数）：关节空间插值的段（移到零件 / 料盒上方）与指尖走直线的段（竖直下降、抬起，每帧解一次逆运动学）分开；夹爪开口按零件被夹处的宽度（电阻 2.9、电容 8、LED 5、螺丝杆 2.5 mm）。关节空间直接运动途中会碰撞时先经过初始姿态。单元测试检查全程每段中间姿态都不碰撞。

#### 步骤 14：网页端 ONNX 推理

**目标：** 网页里用 onnxruntime-web 跑 YOLO，结果与 Python 一致。

**实现要点：**
- `detector.worker.js`：在 Web Worker 里加载模型，`executionProviders: ['webgpu', 'wasm']`；wasm 文件放在 `public/ort/` 并正确设置路径。

- 后处理按输出形状自动判断：
  - `[1, N, 6]`（端到端）：按 `scoreThreshold` 过滤即可
  - `[1, 4 + 类别数, N]`：解码后做 NMS（`iouThreshold`）
- 把框按缩放比例和填充量还原到原图像素。
- 信息面板显示：推理后端（WebGPU / WASM）、模型加载耗时、推理耗时、检测数量。
- 先用官方 `yolo26n` 导出的 COCO 模型和一张含常见物体（杯子、瓶子等）的照片打通流程，再换成 `best.onnx`。

- （实现补充）
  - onnxruntime-web 1.30.0：设备支持 WebGPU 时在 Worker 里加载默认入口（JSEP 版，`['webgpu', 'wasm']`），否则加载纯 WASM 入口（wasm 文件小一半）；WebGPU 初始化失败也回退到 WASM。Vite 配置加了 `onnxruntime-web-use-extern-wasm` 条件，wasm 只从 `public/ort/` 加载（`scripts/copy-ort.mjs` 在 dev / build 前复制，不进仓库），不再重复打包进 assets。GitHub Pages 不能设置跨源隔离响应头，WASM 只能单线程。
  - 前处理、后处理是纯函数（`src/vision/yolo.js`）：取整用 Python 的 round（.5 取偶）、缩放采样位置与 OpenCV INTER_LINEAR 相同、框还原横竖分别用取整后的缩放比，都照 ultralytics 源码。
  - 推理结果做同类去重（`DETECT.dedupIou = 0.7`）：步骤 13 的模型偶尔对同一零件出两个框（训练报告），这两个框的分数对输入的微小差异很敏感。mock 检测文件同样去重。
  - 信息面板：检测方式（模型推理 / mock）、模型（零件模型 / 官方 COCO 调试）、后端（自动 / 仅 WASM）可切换；显示推理后端、模型加载耗时（下载 + 初始化）、推理耗时（前处理 + 推理 + 后处理）、检测数量（原始 → 去重后）。合成图默认用真值框（mock），其他照片默认模型推理。
  - 示例列表加入 3 张真实照片（`public/samples/real/`，步骤 13 的测试集）。
  - 颜色分割补漏（`src/vision/colorSeg.js`，做法同 `training/autolabel.py`）：在标定用的缩小图上，只在零件区域内取红色（LED）、蓝色（电阻）像素，闭运算后取连通块外接框。颜色分割几乎不漏但框常偏大，所以以 YOLO 为准：颜色框附近（IoU > 0.1 或中心互相落入）没有任何 YOLO 框时才补上（置信度记 0.5，调试视图里画虚线、标"颜色"）。面板可关闭，只对零件模型生效。实测 3 张真实照片和合成图：颜色候选数与 YOLO 去重后的框数相同、类别一致、IoU 0.81–0.98，没有多补；耗时 0.3–1 秒。
  - 3D 板面（工具栏"板面"）：默认"纯色"——用标定板的设计版面（白纸 + 码 + 版面文字）按实测纸张位置贴上，照片里的阴影、折痕都不出现；"照片"为擦掉零件后的照片正射图，"照片原图"不擦。

- [ ] WebGPU 不可用时自动回退到 WASM，结果不变

#### 步骤 15：端到端联调

**目标：** 上传一张真实照片，一键跑完全部流程。

**实现要点：**
- 上传照片后自动执行：内参 → 识别 → 单应性 → 位姿 → 检测（默认 onnx 模式，可切回 mock）→ 映射 → 建场景 → 转场；分拣由用户点"开始"触发。
- 内参来源可切换（EXIF / 标定文件），切换后从位姿开始自动重算。
- 每一步记录耗时，信息面板显示分步耗时和总耗时。
- 任何一步出错，步骤条对应项变红，面板显示原因。

- （实现补充）
  - 流程原本就是按状态事件串起来的（照片读入 → 标定 → 位姿 → 检测 → 映射 → 建场景）；这一步补上：场景建好后自动切到 3D 视图播放转场。切换内参来源时识别码、正射图、检测结果都沿用（同一张照片），只从位姿往后重算，停在当前视图。
  - 分步耗时（`src/timing.js`，纯函数）：信息面板"耗时"分区列出读取照片、识别码、单应性 / 正射图、底板贴图、位姿、等待模型加载、检测、颜色分割、映射 / 朝向、建场景，以及总耗时（墙钟，从选好照片到转场开始）和"其他"（界面刷新等）。沿用的步骤显示"沿用"。
  - 提速：页面空闲时预先加载零件模型（Worker 里下载、初始化），上传照片后不用等模型；颜色分割挪到模型推理期间做（照片交给 Worker 后主线程是空的）；两次正射变换共用一份原图像素（`bitmapPixels` 缓存最近一张），不再读两遍 1200 万像素。
  - 出错：识别不到码时"标定"变红；模型推理失败或 mock 模式找不到检测文件时清掉上一次的零件、回到"位姿已求出"，"检测"变红，可以点"框选"手动框出零件后接着往下走。模型加载失败后下次检测会重试。
  - 实测（无头 Chrome，WASM 单线程，CPU 软件渲染）：3 张真实照片从上传到转场开始 3.0–3.4 s（未优化前 3.3–5.6 s），其中模型推理 1.5–2.2 s；切换内参来源到场景建立 0.3–0.4 s。

**验收标准：**
- [ ] 【需要用户】3 张新拍的真实照片都能一键跑完全流程并完成分拣
- [ ] 从上传到转场开始，总耗时 ≤ 5 秒
- [ ] 切换内参来源后结果正常更新
