## 1. 项目简介

用户用 iPhone 13 Pro 拍一张照片，照片里是一块贴有 4 个 ArUco 码的 A4 底板，底板上放着若干电子零件。网页依次完成以下工作：

1. 读取照片和 EXIF，得到相机内参
2. 识别 ArUco 码，求出"底板毫米坐标 → 图像像素"的单应性矩阵 H，并生成底板正射图
3. 由 H 和内参反推拍照时手机的位置和朝向
4. 用 YOLO26n（ONNX）检测零件，把检测框映射到底板毫米坐标（支持视差修正）
5. 在 Three.js 里按真实尺寸重建桌面、底板、零件和拍照的手机，并播放"照片 → 3D"转场动画
6. 虚拟机械臂用逆运动学依次抓取零件，放进对应类别的料盒

整个系统是纯前端静态网页，不需要后端。

## 4. 坐标系约定（所有模块必须统一）

| 坐标系 | 原点 | 轴向 | 单位 |
| --- | --- | --- | --- |
| 图像 | 照片左上角（已按 EXIF 方向转正） | u 向右，v 向下 | 像素 |
| 底板（世界） | 底板靠近操作者的左下角 | X 向右，Y 远离操作者，Z 垂直板面向上（右手系） | mm |
| OpenCV 相机 | 镜头光心 | x 右，y 下，z 沿拍摄方向 | mm |
| Three.js | 与底板原点相同 | x = X，y = Z，z = −Y | 1 单位 = 1 mm |

- 底板坐标 ↔ Three.js 坐标的转换只写在 `src/math/coords.js` 里（`toThree(X, Y, Z)`、`fromThree(v)`），其他地方一律使用底板坐标。
- 位姿约定：底板点 Pw 变换到相机坐标为 Pc = R·Pw + t，手机光心在底板坐标系里的位置为 C = −Rᵀt。
- H 的方向：底板 (X, Y, 1) → 像素 (u, v, 1)。Hinv 方向相反。

## 5. 数据接口

在 `src/state.js` 里用 JSDoc 定义以下类型，各模块函数的输入输出都使用这些类型：

```js
/** 照片 */
ImageInput = { bitmap, width, height, fileName,
               exif: { focal35, focalMm, lensModel, make, model } }

/** 模块 1：内参（对应当前照片的实际分辨率和方向） */
Intrinsics = { fx, fy, cx, cy, width, height, source: 'exif' | 'calib' | 'truth' }

/** 模块 2 */
Marker     = { id, corners: [[u,v],[u,v],[u,v],[u,v]] }  // 顺序：码自身的左上、右上、右下、左下
BoardCalib = { markers: Marker[], H, Hinv, reprojErrPx, rectified /* canvas */ }

/** 模块 3 */
CameraPose = { R /* 3×3 */, t /* [3] */, position /* C: [X,Y,Z] */,
               heightMm, pitchDeg, reprojErrPx }

/** 模块 4 */
Detection = { cls, name, score, box: [x1, y1, x2, y2] }  // 原图像素
Part      = { id, cls, name, score, x, y, heightMm,
              xPlane, yPlane,      // 方法 1（不修正）的结果
              reachable }           // x, y 为当前选用方法的结果

/** 模块 6 */
PickTask  = { partId, binId, from: [x, y, z], to: [x, y, z] }

/** 合成图真值（步骤 3 生成） */
GroundTruth = { intrinsics, R, t, position, pitchDeg,
                markers: Marker[],
                parts: [{ cls, x, y, heightMm, box }] }
```

流程状态机：`idle → imageLoaded → calibrated → posed → detected → sceneBuilt → sorting → done`。每一步写入 state 后发出事件；某一步失败时停在当前状态，信息面板显示原因，并允许单独重跑这一步。

#### 步骤 3：合成测试图生成器

**目标：** 在还没有真实照片的情况下，生成带精确真值的"假照片"，用来自动检验后面每个模块算得对不对。

**实现要点：**
- `synth.html`：用 Three.js 离屏渲染一张 4032 × 3024 的图片。内容包括：
  - 一个桌面
  - 底板，表面贴步骤 2 的标定板图案
  - 按一份布局 JSON 摆放的 8–10 个零件（每类用简单几何体，颜色取 `CLASSES.color`，高度取 `heightMm`）
- 虚拟相机使用 iPhone 13 Pro 的内参（fx = fy ≈ 3028，主点在图像中心），按设定的位姿放置。
- 预设 3 个视角：俯角 90°（正上方）、65°、45°，相机离底板中心约 300 mm。斜拍的两张另加少量偏航（65°：6°；45°：−8°，并滚转 2°），避免只测完全对称的情况。
- 像素坐标约定：像素 (i, j) 覆盖 [i, i+1) × [j, j+1)，中心在 (i+0.5, j+0.5)，主点在图像中心时 cx = W/2、cy = H/2（与 Three.js 渲染一致）。
- 零件模型写在 `scene/parts.js`（`PART_SIZE` 包围盒尺寸 + `createPartMesh`），步骤 10 复用；布局在 `src/synth/layout.json`。合成图里的桌面比视野大（1600 × 1200 mm），只作背景。
- synth.html 提供"渲染自检"：在渲染图上识别码，与真值角点比较，用来确认渲染端的坐标转换（`coords.js` 的 `cameraQuaternionFromR`）与针孔公式一致。
- 输出两个文件，存进 `public/samples/`：
  - PNG 图片
  - `GroundTruth` JSON：内参、R、t、手机位置、俯角、每个码 4 个角点的像素坐标、每个零件的 (x, y)，以及零件 3D 包围盒投影到图像上得到的 box
- **注意：** 真值里的角点像素坐标和零件 box 要用纯数学的针孔投影公式计算（K·(R·P + t)），不能从 Three.js 里读，否则后续模块和生成器如果共用同一个错误的转换，误差会互相抵消，看不出来。
- 主页面"加载示例"下拉框里能选这 3 张合成图。加载合成图时，内参直接取真值（`source: 'truth'`）；之后每个模块完成，信息面板都自动显示"与真值的误差"。

**验收标准：**
- [ ] 3 张合成图看起来像不同角度拍的底板，码清晰
- [ ] 调试视图里，把真值角点和零件 box 画在合成图上，都和图像内容对齐
- [ ] `npm test` 包含针孔投影函数的测试，并且通过

### 阶段二：视觉几何

#### 步骤 4：读取照片与相机内参（模块 1）

**目标：** 正确读入照片（方向、尺寸、EXIF），算出内参。

**实现要点：**
- `image.js`：用 `createImageBitmap(file, { imageOrientation: 'from-image' })` 按 EXIF 方向转正；用 exifr 读 `FocalLengthIn35mmFormat`、`FocalLength`、`LensModel`、`Make`、`Model`。HEIC/HEIF 文件直接提示"请在 iPhone 设置 → 相机 → 格式中选择'兼容性最佳'"。
- `intrinsics.js` 导出纯函数：
  - `fromExif(focal35, width, height)`：f = focal35 × √(W² + H²) ÷ 43.27，fx = fy = f，cx = W/2，cy = H/2
  - `fromCalib(calib, width, height)`：读 `intrinsics.json`（参考分辨率 4032 × 3024，横向）
    - 分辨率不同时，fx、fy、cx、cy 都乘以 s = 实际宽 ÷ 参考宽
    - 竖拍（顺时针转 90°）时，fx' = fy，fy' = fx，cx' = 参考高 − cy，cy' = cx
- 镜头检查：`focal35 ≠ 26` 时，信息面板显示黄色警告"可能切换了镜头（当前等效焦距 xx mm）"。
- （实现补充）`fromCalib` 增加可选第 4 个参数 rotation（照片相对传感器顺时针旋转的角度，由 EXIF Orientation 得到：6 → 90°、3 → 180°、8 → 270°），省略时按宽高判断，竖图视为顺时针 90°；`ImageInput.exif` 增加 `orientation`。标定文件格式：`{ fx, fy, cx, cy, width, height, dist, rms }`，未标定时 `public/intrinsics.json` 为只含说明的占位文件。
- （实现补充）照片没有 EXIF（例如微信转发未选"原图"）时按默认 26 mm 估算并提示。默认来源：合成图用真值；有标定文件且是主摄、宽高比一致时用标定文件；否则用 EXIF。
- 信息面板显示：文件名、分辨率、等效焦距、镜头型号、fx、内参来源。界面上可以切换 EXIF / 标定文件（没有 `intrinsics.json` 时禁用该选项）。

**单元测试：** (26 mm, 4032 × 3024) → fx 在 3028 ± 1；竖拍换算；分辨率缩放。

**验收标准：**
- [ ] 【需要用户】上传一张 iPhone 横拍 JPEG 和一张竖拍 JPEG，调试视图里方向都正确
- [ ] 横拍照片面板显示 4032 × 3024、26 mm、fx ≈ 3028
- [ ] 上传 HEIC 文件时出现格式提示
- [ ] `npm test` 通过

#### 步骤 5：ArUco 识别（模块 2 上半部分）

**目标：** 稳定识别 4 个码，并输出约定顺序的角点。

**实现要点：**
- `aruco.js`：把照片缩小到长边 1600 像素再识别，角点坐标按比例换回原图像素。只保留 ID 0–3，同一 ID 出现多次时保留面积最大的那个。

- （已在步骤 2 提前完成）多轮识别以适应打印斑点；角点精修到亚像素。
- （实现补充）照片读入后自动识别；识别结果在步骤 6 求出单应性后与 H 一起写入 `state.calib`（BoardCalib），步骤 5 只在信息面板和调试视图展示。一个码都没识别到时步骤条"标定"变红；"重新识别"按钮单独重跑这一步。与真值的比较函数在 `vision/evaluate.js`，后续模块复用。
- 调试视图叠加层：画出每个码的四边形和 ID，第一个角点（左上）画红点。

**验收标准：**

#### 步骤 6：单应性与正射图（模块 2 下半部分）

**目标：** 求出 H，生成"从正上方看"的底板图。

**实现要点：**
- `homography.js` 纯函数：
  - `solveHomography(worldPts, imagePts)`：归一化 DLT。两组点各自平移到质心、缩放到平均距离 √2，构造 2N × 9 矩阵，用 ml-matrix 做 SVD 取最小奇异值对应的向量，最后反归一化。
  - `applyH(H, p)`、`invert3(H)`、`reprojError(H, worldPts, imagePts)`
- 角点的底板坐标：码中心 (cx, cy)、边长 s 时，左上 (cx − s/2, cy + s/2)，右上 (cx + s/2, cy + s/2)，右下 (cx + s/2, cy − s/2)，左下 (cx − s/2, cy − s/2)。
- 至少 1 个码就计算；少于 4 个码时给出精度警告。重投影误差 > 3 像素时提示重拍。
- `rectify(bitmap, H, pxPerMm = 2)`：输出 594 × 420 的 canvas。画布第 i 行第 j 列对应底板坐标 X = j / 2，Y = 210 − i / 2（画布顶部是底板远端），用 H 找到原图像素并取色（双线性插值）。
- 调试视图增加一个"正射图"小窗。
- （实现补充）按项目的像素约定取像素中心：第 i 行第 j 列对应 X = (j + 0.5) / 2，Y = 210 − (i + 0.5) / 2（与上面的公式差半个像素，即 0.25 mm）；超出原图的区域透明。采样部分是纯函数 `rectifyPixels`，`rectify` 只负责 canvas。由码求 H 的流程为 `boardHomography`（含少于 4 个码、重投影误差 > 3 像素的提示）。正射图小窗上用虚线画出设计的码位置，便于检查。合成图另外显示"单应性 vs 真值"：底板上每 10 mm 一个点，比较 H 与真值位姿的投影。

**单元测试：** 用已知 H 生成点对，能恢复出 H；加 0.5 像素噪声后重投影误差 < 1 像素。

**验收标准：**
- [ ] 合成图的重投影误差 < 1.5 像素；真实照片 < 3 像素
- [ ] 正射图方正不变形：ID3 在左上、ID2 在右上、ID0 在左下、ID1 在右下，码都是正方形
- [ ] `npm test` 通过

#### 步骤 7：手机位姿反推（模块 3）

**目标：** 由 H 和 K 求出拍照时手机的 R、t 和位置。

**实现要点：**
- `pose.js` 纯函数 `poseFromHomography(K, H, worldPts, imagePts)`：
  1. B = K⁻¹H，三列记为 b₁、b₂、b₃
  2. λ = 2 ÷ (‖b₁‖ + ‖b₂‖)；r₁ = λb₁，r₂ = λb₂，t = λb₃
  3. 若 t 的 z 分量 < 0，r₁、r₂、t 全部取反
  4. r₃ = r₁ × r₂，R = [r₁ r₂ r₃]；用 SVD 正交化：R = U·Vᵀ
  5. C = −Rᵀt；heightMm = C 的 Z 分量
  6. 光轴方向 d = Rᵀ·(0, 0, 1)，pitchDeg = asin(−d_z)（90° 表示垂直向下拍）
  7. 用 K[R | t] 重投影全部角点，求平均误差 reprojErrPx
- 调试视图增加"位姿叠加"开关：用 K[R | t] 把底板外框、4 个码的方框和底板坐标轴（X 红、Y 绿、Z 蓝，长 100 mm）投影画在原图上。
- 信息面板显示："手机离桌面 xx.x cm，俯角 xx.x°，重投影误差 x.xx 像素"。
- （实现补充）按上述 7 步实现，未加非线性优化：单元测试中 0.5 像素噪声下最大位置误差约 1.4 mm、角度误差约 0.15°，已满足要求。位姿重投影误差明显大于单应性重投影误差时提示"内参可能不准"。求出的高度 ≤ 0 时视为失败。合成图显示位置 / 俯角 / 姿态相对真值的误差（`evaluate.js` 的 `poseTruthError`）。

**单元测试（纯数学，不经过 Three.js）：** 随机生成 20 组位姿（高度 250–500 mm，俯角 40°–90°），用针孔模型投影角点：无噪声时位置误差 < 0.1 mm；加 0.5 像素噪声时位置误差 < 5 mm，角度误差 < 0.5°。

**验收标准：**
- [ ] 3 张合成图：位置误差 < 5 mm，俯角误差 < 0.5°（面板显示与真值对比）
- [ ] 真实照片打开位姿叠加，底板外框和码方框贴合照片里的实物
- [ ] 【需要用户】拍照时用卷尺量镜头离桌面的高度，与系统给出的高度相差 < 5%
- [ ] `npm test` 通过

### 阶段五：机械臂与分拣

#### 步骤 11：机械臂模型与逆运动学

**目标：** 机械臂能把指尖准确送到底板上任意一点。

**实现要点：**
- `ik.js` 纯函数（坐标都相对底座）：
  - `ik(target, ARM)`：
    - θ₀ = atan2(y, x)，r = √(x² + y²)，z' = z + L3 − L0
    - D = (r² + z'² − L1² − L2²) ÷ (2·L1·L2)；|D| > 1 时返回 `reachable: false`
    - θ₂ = −arccos(D)（肘部朝上）
    - θ₁ = atan2(z', r) − atan2(L2·sin θ₂, L1 + L2·cos θ₂)（从水平面量起）
    - θ₃ = −π/2 − θ₁ − θ₂（保证夹爪竖直向下）
  - `fk(angles, ARM)`：返回指尖位置，用于测试和显示
- `arm.js`：用 Three.js 基础几何体搭出层级结构：底座（绕 Z 旋转）→ 肩关节 → 大臂 → 肘关节 → 小臂 → 腕关节 → 夹爪（两根手指，可开合）。外观干净、工业风。
- `bins.js`：按 `BINS` 摆放开口料盒，盒子侧面写类别名。
- 调试模式：在 3D 视图里点击底板任意位置，机械臂运动到该点正上方 `approach` 高度处，信息面板显示 fk 计算的指尖位置与目标的误差；够不到的点显示红色提示。

**单元测试：** 在可达范围内随机取 200 个点，`fk(ik(p))` 与 p 的误差 < 0.01 mm；明显超出范围的点返回不可达。

**验收标准：**
- [ ] 点击底板四个角附近和中心，指尖都准确到达（面板误差 < 0.1 mm）
- [ ] 动作中各段连杆不脱节，夹爪始终竖直向下
- [ ] 6 个料盒都在可达范围内
- [ ] `npm test` 通过

#### 步骤 12：分拣规划与抓取动画

**目标：** 机械臂自动把全部零件分拣进对应料盒。

**实现要点：**
- `planner.js` 纯函数 `plan(parts, BINS, ARM) → { tasks: PickTask[], skipped: Part[] }`：先排除不可达零件，然后用贪心最近邻排序（从当前夹爪位置出发，每次选最近的零件）。
- 每个零件的动作序列：
  1. 移到零件正上方 `approach` 高度
  2. 下降到零件半高处
  3. 夹爪闭合，用 Three.js 的 `attach` 把零件挂到夹爪节点下
  4. 抬起到 `approach` 高度
  5. 移到对应料盒正上方
  6. 下降、夹爪张开，把零件挂回场景，落在盒内（同一盒内的零件依次错开或堆叠）
- 相邻关键姿态之间做关节角插值，加 easeInOutCubic 缓动，每段 0.4–0.8 秒。
- 界面：任务列表（执行中的一项高亮、完成的打勾）、开始 / 暂停 / 重置按钮、速度滑块（0.5×–3×）。不可达零件标红，并列在"已跳过"里。
- 重置后，零件回到原位，机械臂回到初始姿态。

**单元测试：** 规划结果里每个可达零件恰好出现一次，料盒与类别对应；相同输入得到相同顺序。

**验收标准：**
- [ ] 合成图示例：全部零件依次放进正确的料盒，没有零件悬空、穿模或掉出盒子
- [ ] 暂停、继续、调速、重置都正常
- [ ] `npm test` 通过

#### 步骤 14：网页端 ONNX 推理

**目标：** 网页里用 onnxruntime-web 跑 YOLO，结果与 Python 一致。

**实现要点：**
- `detector.worker.js`：在 Web Worker 里加载模型，`executionProviders: ['webgpu', 'wasm']`；wasm 文件放在 `public/ort/` 并正确设置路径。
- 前处理：等比缩放到 1024，空白处填灰 (114, 114, 114)，转 RGB、除以 255、排成 NCHW 的 Float32Array。
- 后处理按输出形状自动判断：
  - `[1, N, 6]`（端到端）：按 `scoreThreshold` 过滤即可
  - `[1, 4 + 类别数, N]`：解码后做 NMS（`iouThreshold`）
- 把框按缩放比例和填充量还原到原图像素。
- 信息面板显示：推理后端（WebGPU / WASM）、模型加载耗时、推理耗时、检测数量。
- 先用官方 `yolo26n` 导出的 COCO 模型和一张含常见物体（杯子、瓶子等）的照片打通流程，再换成 `best.onnx`。

**验收标准：**
- [ ] 同一张图片，网页结果与 `predict_dump.py` 结果的数量相同，框坐标相差 < 2 像素
- [ ] 换成 `best.onnx` 后，真实照片的检测框在调试视图里位置正确
- [ ] WebGPU 不可用时自动回退到 WASM，结果不变

#### 步骤 15：端到端联调

**目标：** 上传一张真实照片，一键跑完全部流程。

**实现要点：**
- 上传照片后自动执行：内参 → 识别 → 单应性 → 位姿 → 检测（默认 onnx 模式，可切回 mock）→ 映射 → 建场景 → 转场；分拣由用户点"开始"触发。
- 内参来源可切换（EXIF / 标定文件），切换后从位姿开始自动重算。
- 每一步记录耗时，信息面板显示分步耗时和总耗时。
- 任何一步出错，步骤条对应项变红，面板显示原因。

**验收标准：**
- [ ] 【需要用户】3 张新拍的真实照片都能一键跑完全流程并完成分拣
- [ ] 从上传到转场开始，总耗时 ≤ 5 秒
- [ ] 切换内参来源后结果正常更新
